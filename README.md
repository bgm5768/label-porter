# 라벨 포터

**버전 관리 기준: v1 (2026-10-20)** — 프로그램 2.4.0을 첫 Git 기준 버전으로 보관합니다. `v1` 태그로 이 상태를 다시 확인할 수 있습니다. 현재 프로그램은 **2.27.0**이며 변경 내역은 [CHANGELOG.md](CHANGELOG.md)에 기록합니다.

플랫폼 DB에 접근하지 않고, 어드민에서 내려받은 작업 결과를 원본 라벨링 JSON에 반영하는 Windows 데스크톱 프로그램입니다. 모든 데이터 처리는 로컬에서 이루어집니다. 외부 서비스나 AI 호출이 없습니다.

원본은 읽기만 합니다. 폴더 선택은 폴더 전체를, 파일 다중 선택은 선택 파일만 새 폴더에 복사하고, 연결키가 확인되고 검증을 통과한 레코드의 지정 필드만 수정합니다. 결과에 없는 파일·레코드는 보존합니다. 목록 내부의 추가·삭제는 사용자가 선택한 규칙에 따릅니다.

**2.4 개선:** 결과 목록으로 전체 재구성하는 규칙을 추가했습니다. 사용자가 전체 교체를 선택한 경우 어절 추가·삭제·분할·병합도 반영합니다. 독립된 발음 오류 태그는 수정 규칙에 포함하지 않으면 원본 그대로 유지됩니다. 참조 재연결·불확실한 태그의 별도 보관은 규칙에서 명시적으로 선택한 경우에만 수행합니다. 왼쪽 아래 **JSON 뷰어**에서 최상위 항목 수와 내부 배열 개수를 확인할 수 있습니다. 2.3의 보고서 페이지 이동·전체 검색·대용량 분할 읽기도 유지됩니다.

**AI 규칙 흐름:** AI 규칙 작성을 기본 흐름으로 사용합니다. 원본 라벨·플랫폼 결과·MD 가이드를 AI에 전달하고 받은 규칙을 불러옵니다. ‘필드 연결’ 탭은 연결된 기준·수정값·반복 목록·기존값 검사만 읽기 전용으로 보여 줍니다. ‘필드 연결 프리뷰’에서는 전체 입력을 검색·페이지 이동하고 레코드를 선택하여 실제 연결값과 적용 후 JSON을 확인합니다. 읽은 데이터와 화면 상태는 다른 단계에 다녀와도 유지됩니다. 수정은 가이드·현재 규칙·요청 내용을 AI에 전달해 새 규칙을 받습니다. 실제 데이터는 입력 단계에서 한 번 선택하고 전체 검증 후 복사본에 반영합니다.

## 처리 결과서

집계 카드를 누르면 작업 결과·처리 완료·원본·보완·변경 필드·검토/오류·짝이 없는 데이터·조건 제외·파일 오류 목록으로 이동합니다. 분류 및 상태 필터, 변경된 필드 드롭다운, 전체 검색, 25/50/100건 페이지 이동을 함께 사용합니다. 필드 목록은 실제 변경 기록에서 만들며 필드별 원본 레코드 수를 표시합니다. 필드를 선택하면 해당 변경이 있는 레코드만 보이고, 변경 필드 분류에서는 해당 경로의 변경 행만 보입니다. 상세 비교 후 돌아와도 선택한 필터와 페이지가 유지됩니다. 정상 완료 항목도 상세 비교에서 원본·보완·출력 JSON과 변경 전후 값을 확인할 수 있습니다.

작업 결과는 원본을 기준으로 처리 상태가 확정된 레코드입니다. 완료는 검토 사유 없이 반영되었거나 값이 같은 레코드입니다. 변경 필드는 규칙이 기록한 변경 경로 수이며 목록 전체 교체는 1개로 집계합니다. 원본/보완은 서로 다른 입력이고 오류는 양쪽에 기록될 수 있어 카드를 합산하지 않습니다. 보고서는 인터넷 없이 동작하며 `reports` 폴더 전체를 함께 보관하세요.

## 실행

- Windows 실행 파일: `dist/v2.27.0/LabelPorter.exe`를 더블클릭합니다. Python 설치가 필요하지 않습니다.
- 소스 실행: Python 3.11 이상에서 `python -m label_porter` 또는 `start.cmd`를 실행합니다. 먼저 `python -m pip install -r requirements.txt`로 CustomTkinter와 문서 뷰어 의존성을 설치합니다. Windows 공식 Python의 Tkinter 위에 CustomTkinter 화면을 구성합니다. 실행 파일에는 문서 뷰어가 내장되어 별도 설치가 필요 없습니다.
- 상세 규칙 설명: [사용설명.md](사용설명.md)
- 후처리 가능 수준과 제한: [후처리_지원범위.md](후처리_지원범위.md) — 프로그램의 사용 방법 화면에도 포함됩니다.
- 전체 구조와 자체 규칙 엔진: [아키텍처_및_규칙엔진.md](아키텍처_및_규칙엔진.md) — 사용 방법의 마지막 **아키텍처 · 규칙 엔진** 탭에도 포함됩니다. 계층별 구조, 규칙 문법, 실행 흐름, 프리뷰·저장·보고서와 코드 위치를 설명합니다.

## 화면에서 사용하기

**‘데이터로 규칙 만들기’에서 서로 다른 필드도 연결할 수 있습니다.** 원본 폴더와 플랫폼/보완 파일을 선택 → 연결 기준 추천 또는 직접 선택 → 반영 항목 체크 또는 직접 연결 → 검색·페이지별 실제 전후 확인 → 규칙 생성 → 기존 전체 검증·저장으로 이어집니다. AI나 별도 네트워크 연결이 필요하지 않습니다. 생성한 규칙은 ‘규칙 내보내기’로 저장할 수 있습니다.

- JSON / JSONL / NDJSON, 개별 파일·통합 배열·일반적인 records/rows/items/data 래퍼를 지원합니다. 원본 폴더의 JSON 계열 확장자는 한 종류씩 선택합니다.
- 연결 기준의 누락·중복·연결 수는 전체 입력을 검사합니다. 필드 위치는 구조 표본에서 탐색하고, 변경 예시는 앞 200개 연결 쌍을 사용합니다. 추천이 없어도 ‘직접 선택’으로 원본·보완 KEY를 따로 고를 수 있습니다. 값이 다르면 연결 수 0으로 표시하며 행 순서로 짝짓지 않습니다.
- 추천 항목을 먼저 표시하고 ‘다른 항목도 보기’ 또는 검색으로 표본의 다른 공통 항목을 찾습니다. 선택하지 않은 값은 원본 유지입니다.
- ‘다른 필드 연결’에서 원본 대상과 가져올 보완 필드를 선택합니다. ‘선택한 연결 수정’으로 연결과 빈 값 처리 정책을 바꿉니다. `importData_*`는 가져온 원본 값일 수 있으므로 실제 수정 입력값을 확인하세요. 단일 항목 내부를 연결하면 배열 길이 검사도 생성합니다.
- 선택한 목록은 순서·ID·추가·삭제·빈 목록·내부 추가 필드까지 보완본 그대로 반영합니다. 시간 반올림, ID 재부여, 전사 재생성, 태그 참조 검사를 자동 추가하지 않습니다. 어절의 음수·역전 시간 검사는 선택할 수 있습니다.
- 단계·도움말 이동과 생성 후 필드 연결 프리뷰에 읽은 데이터를 재사용합니다. 외부 파일 변경은 2단계에서 해당 입력을 다시 선택하여 반영합니다. 3단계는 선택 레코드의 적용 예시만 계산하며, 4단계에서 전체 검증 후 최종 복사본을 저장합니다. 프리뷰 읽기·계산 중에는 4단계로 이동할 수 없습니다.
- 자료형 변환·복잡한 조건·반복 목록 내부 재구성·모호한 레코드 위치·표본에 없는 필드는 아래 AI 규칙 경로를 사용합니다. 전체 결과를 저장하기 전에 처리 결과서를 확인하세요.

**AI 규칙 파일을 사용하는 방법:**

1. 왼쪽 아래 **사용 방법 → AI 규칙 작성 가이드**에서 MD를 저장하거나 복사해 원본·플랫폼/보완 데이터와 함께 AI에게 전달합니다.
2. **규칙 파일 불러오기**로 `project_rule.json`을 엽니다. 같은 화면의 **현재 규칙** 아래에서 **필드 연결 / 규칙 JSON**을 확인합니다. 연결 행을 누르면 세부 설정을 볼 수 있으며, **규칙 내보내기**는 그 아래에 있습니다. **다음 단계**를 누르면 데이터 선택으로 이동합니다.
3. 원본과 플랫폼/보완 데이터를 각각 **폴더 선택** 또는 **파일 다중 선택**으로 지정합니다. 양쪽 모두 **선택 제거 / JSON 미리보기**가 있습니다. 뷰어에서 파일명·경로 검색과 100개 단위 페이지 이동으로 원하는 파일을 열 수 있습니다. 저장 위치도 확인합니다.
4. **필드 연결**과 **필드 연결 프리뷰**를 확인합니다. 전체 목록을 자동으로 불러오며 KEY·파일명·JSON 내용 검색, 연결 상태 필터, 페이지 이동을 지원합니다. 외부에서 파일을 변경했다면 2단계에서 해당 입력을 다시 선택합니다.
5. **3단계 프리뷰 확인 → 4단계 전체 데이터 검증 → 처리 결과서 → 복사본 저장** 순서로 진행합니다.

규칙을 고칠 때는 원하는 변경을 설명하고 가이드·현재 규칙·예시 데이터를 AI에 전달합니다. 새로운 규칙 JSON을 받아 다시 불러옵니다. 프로그램 자체에는 AI 호출이나 데이터 외부 전송 기능이 없습니다. 기존 규칙 문법과 원본 보존·분리·보고서 기능은 유지됩니다.

자세한 내용은 [사용설명.md](사용설명.md)를 참고하세요.

## 출력

자주 누르는 미리보기와 보관해야 할 반영 결과를 구분합니다.

```text
선택한 저장 폴더/
  검증/실행ID/미리보기/    GUI 검증별 보고서 (이전 검증 유지)
    reports/
    rule.json
    manifest.json
    run_status.json
  2026-10-19/
    001/                  이날 첫 번째 반영
      data/               원본 폴더 구조를 유지한 전체 복사본
      changed/labels/     검토 사유 없이 실제 변경된 라벨
      unchanged/labels/   값 동일 라벨
      examine/unmatched/     짝이 없는 데이터
      examine/review/        검토 / 오류
      examine/excluded/      조건 제외
      examine/file_errors/   파일 단위 오류
      reports/
        report.html       분류별 검색·페이지 이동이 있는 처리 결과서
        report.xlsx       보완 요약·상세 이력·예시·검토·전후 JSON을 보는 Excel 결과서
        report_data.jsonl 작업 ID로 연결되는 버전 있는 결과서 원문·Excel 재병합용
        catalog.json      원본·보완·출력·완료·검토·누락·변경 필드 목록
        record_details.jsonl 모든 처리 항목의 원본·보완·출력 JSON
        detail.html       공통 레코드 상세 화면
        detail_data/      필요할 때만 불러오는 상세 데이터 묶음
        summary.json      기계가 읽는 집계
        records.csv       전체 상태·누락·중복·검토 사유
        changes.jsonl     필드별 변경 전후 값
        review_details.jsonl 전체 검토 사유·원본·플랫폼·실제 출력·후보 JSON
        review/           검토 레코드별 비교 HTML 및 전체 JSON
        partition_index.jsonl 원본 ↔ 분리본 위치
      rule.json        적용 규칙
      manifest.json       원본/결과 해시
      run_status.json     완료·검토·실패·중단 상태
    002/                  이날 두 번째 반영
  2026-10-20/
    001/                  다음 날 첫 번째 반영
```

GUI 저장 위치를 지정하지 않으면 `%LOCALAPPDATA%/LabelPorter/workspace/results`를 사용합니다. 실행 파일을 옮기거나 업데이트해도 보관함은 유지됩니다. 직접 선택한 보관 경로에는 `포팅결과`를 덧붙이지 않습니다.

날짜는 **한국 시간** 기준입니다. 순번은 같은 날짜 폴더의 가장 큰 숫자 다음으로 발급하며 999 다음에는 1000입니다. 미리보기는 순번을 사용하지 않습니다. 기존 실제 반영 결과와 이전 버전의 `run_...`, `preview_...` 폴더는 이동하거나 삭제하지 않습니다.

GUI 미리보기는 `검증/실행ID/미리보기`에 매번 새로 생성하여 이전 결과를 유지합니다. CLI `run --preview`는 기존처럼 지정 출력 아래의 `미리보기`를 재사용합니다. 자동 설정 저장은 메타데이터만 기록하며 결과물을 재작성하지 않습니다.

왼쪽 **작업 보관함**에서 검색·종류 필터·페이지 이동으로 이전 작업을 찾고 버튼·더블클릭·Enter로 규칙과 입력 선택을 복원합니다. HTML/Excel 열기, 폴더 열기, Excel 다른 이름으로 저장, 전체 결과 ZIP 내보내기를 제공합니다. 기본 보관함의 `history.sqlite3`에 실행 위치와 설정을 기록하고 결과서 병합도 이 목록에서 선택합니다. **작업 삭제**는 목록에서만 제거하며 자동 검색으로 되살아나지 않습니다. **결과 파일까지 삭제**는 프로그램 전용 보관함 내부 결과만 대상으로 하며 외부 지정 폴더와 입력 파일은 유지합니다. 과거 결과는 알려진 저장 위치에서 찾아 등록하며 다른 위치는 **기존 결과 폴더 등록**으로 추가합니다. 파일 자체는 이동·중복 저장하지 않습니다. 결과서 병합 산출물은 보관함의 `merged`에 자동 저장·등록됩니다.

실패/중단된 반영에는 부분 복사본이 남을 수 있으며, `run_status.json`과 HTML 보고서에 표시합니다. 다음 실행은 새 순번으로 저장됩니다. 실패/중단된 결과를 완성본으로 사용하지 마세요.

통합 JSON은 레코드 단위로, 개별 JSON은 파일 단위로 분리합니다. 원래 파일명·상대 경로·라벨 구조를 유지하며 통합 JSON의 바깥 메타데이터는 변경하지 않습니다. 검토·오류·연결 누락 대상은 `examine`에 분리하며 정상 변경/미변경 그룹에 중복으로 넣지 않습니다. 결과 없는 원본과 원본 없는 보완 데이터는 따로 집계합니다. 검토 대상에 연결된 보완 데이터도 분류별 `보안`에 저장합니다. `원본`은 처리 전 원본이고, 실제 처리 후 값은 `data`에 있습니다. 정상 데이터 분리를 꺼도 examine은 저장합니다. 미리보기는 분리 예정 집계만 계산하고 데이터 파일을 만들지 않습니다.

분리 대상은 라벨 JSON입니다. 원본 폴더에 함께 들어 있는 다른 파일은 전체 `data/` 복사본에 보존합니다. 별도 원천데이터 폴더를 연결하거나 이미지·오디오를 두 그룹으로 분리하는 기능은 없습니다. 예전 규칙 파일의 `assets` 설정은 불러올 때 제외되며 라벨 반영 규칙은 유지됩니다.

## 보존 및 검증 정책

- 결과에 없는 원본은 그대로 보존하며 `no_result`로 보고합니다. 이것만으로 작업 누락이라고 판정하지 않습니다.
- 원본 키/결과 키가 중복되면 임의로 하나를 선택하지 않습니다. 관련 항목 전체를 보존하고 보고합니다.
- 빈 수정값·필드 누락·자료형 오류·동일성 확인 실패·시간 범위/참조 오류는 `review_required`입니다.
- 레코드 내 여러 필드 중 하나라도 실패하면 해당 레코드의 모든 변경을 취소합니다. 다른 정상 레코드는 반영할 수 있습니다.
- 원본의 다른 필드와 메타데이터, 미디어 파일, 결과에 없는 파일은 유지됩니다.
- 결과에 없는 배열 항목은 기본적으로 검토 대상입니다. 부분 결과임이 확실한 프로젝트는 `require_same_keys: false`로 기존 항목을 보존하며 처리할 수 있습니다.
- 새 객체 ID, 어절 분할/병합의 자동 추정은 하지 않습니다. 관계를 정의한 새 규칙/확장 작업이 필요합니다.
- 설정은 임의 Python/JavaScript를 실행하지 않습니다. 지원하는 연산만 사용합니다.
- 수정된 JSON의 공백/들여쓰기/숫자 표기 등 직렬화 표현은 달라질 수 있습니다. 구조·값·자료형을 보존하며, 수정되지 않은 파일은 바이트 그대로 복사합니다.

기능 수정·일반 빌드·Git 커밋만으로는 버전을 올리거나 업데이트를 게시하지 않습니다. 배포 담당자가 다음 순서를 명시적으로 실행합니다. 아래 `2.27.0`은 예시이며 현재보다 높은 버전을 선택합니다.

```powershell
# 먼저 배포할 소스·테스트·문서 변경을 검토하고 커밋합니다.
.\.venv\Scripts\python.exe scripts/release.py prepare --version 2.27.0
# 갱신된 버전·CHANGELOG·문서를 검토하고 커밋합니다.
```

- `prepare`: 추적 중인 변경이 없는 상태에서 버전과 문서를 갱신합니다. 자동 커밋은 하지 않습니다.
- `build`: 현재 커밋의 파일만 별도 작업 폴더로 꺼내 테스트·Mermaid 검사·실행 파일 빌드·자체 검사를 수행합니다. `dist/v버전`에 실행 파일, 문서, ZIP, `LabelPorter-update.json`을 만듭니다. 기존 배포 폴더는 덮어쓰지 않습니다. 로컬 데이터나 추적되지 않은 파일은 빌드에 들어가지 않습니다.
- `publish`: 비공개 `bgm5768/label-porter` 저장소와 `main`을 확인하고 커밋·태그를 push합니다. GitHub 초안에 ZIP과 업데이트 명세를 모두 업로드한 뒤 정식 릴리스로 게시합니다. 업로드 실패 시 초안으로 남아 사용자의 업데이트 목록에 노출되지 않습니다. 이미 게시된 릴리스·다른 커밋의 태그는 덮어쓰지 않습니다.

유지보수 PC는 Git 인증 또는 `LABEL_PORTER_GITHUB_TOKEN` 환경 변수로 인증합니다. 게시 계정에는 저장소 Contents 쓰기 권한이 필요합니다. 사용자 PC에는 Contents 읽기 권한만 있으면 됩니다. 토큰을 코드·EXE·규칙·배포 파일에 넣지 마세요.

소스 코드, 테스트와 가상 데이터, 규칙 예제, 사용 설명서, 빌드 설정을 관리합니다. 실제 라벨 데이터, 플랫폼 내보내기 파일, 검증 보고서, 실행 파일, 가상 환경, 개인 설정과 인증 정보는 포함하지 않습니다.

작업 데이터는 저장소 밖에 두거나 `.gitignore`에 지정된 `data/`, `inputs/`, `results/`, `outputs/` 폴더를 사용하세요. 개인 프로젝트 규칙은 `local_rules/`에 보관하세요. `rules/`는 배포용 예제이며 특정 작업에 적용하기 전에 조건을 확인해야 합니다. `.gitignore`는 임의 이름의 민감한 파일을 자동 판별하지 않으므로 커밋 전에 추가 파일 목록을 확인하세요.

## 적용 범위

원본은 JSON 기반 라벨링 파일을 지원합니다. 단일 객체, 배열, 중첩 레코드, JSONL, 여러 JSON 객체가 공백으로 이어진 파일을 처리합니다. 결과 입력은 같은 JSON 종류와 CSV를 지원합니다. CSV의 중첩 JSON 열은 설정에 명시해 해석합니다. 이미지·오디오·LLM·3D의 구분보다 **원본과 결과의 연결키, 수정할 필드, 단위, 객체 관계**가 설정의 기준입니다.

임의의 신규 스키마를 의미까지 자동 추론하는 프로그램은 아닙니다. 이미 보완된 구간 분할·병합과 객체 추가·삭제는 목록 재구성 규칙으로 반영할 수 있습니다. 분할·병합 관계의 의미 추론, XML/독자 바이너리 해석, 좌표계 회전은 전처리나 추가 개발 대상입니다. JSON 객체/배열 전체 교체도 명시적으로 설정할 수 있지만 내부 참조와 누락 항목을 프로젝트에서 검증해야 합니다.

## 분류별 개별 후처리 파일

`examine`은 `unmatched`(짝 없음), `review`(검토/오류), `excluded`(조건 제외), `file_errors`(파일 오류)로 나뉩니다. 분류는 중복 없이 저장하며 파일 단위 오류를 먼저 구분합니다.

- 각 분류의 `원본/`에는 처리 전 원본을, `보안/`에는 연결된 플랫폼·보완 입력을 따로 저장합니다.
- 개별 파일은 이름·하위 경로·입력 바이트를 그대로 유지합니다. 보안 파일의 하위 경로는 선택 파일들의 공통 상위 폴더를 기준으로 하므로 같은 이름도 서로 섞이지 않습니다.
- 통합 파일은 `원본/통합파일.json/00000001.json` 또는 `보안/통합파일.json/00000001.json`처럼 해당 레코드만 분리합니다. 번호는 입력 파일 안의 레코드 순번입니다. 한 건짜리 배열·중첩 입력은 원래 파일 자체로 보관합니다.
- 한쪽이 없으면 존재하는 쪽만 저장합니다. 빈 JSON이나 누락된 쪽의 대체 파일·폴더를 만들지 않습니다. 중복 KEY는 임의로 연결하지 않고 후보를 각각 보관합니다.
- `details/00000001.json`은 검토 사유·비교 근거 문서입니다. 라벨 재처리에는 `원본`·`보안` 안의 파일을 사용합니다. `examine_sources`와 `examine_results`에서 해당 건의 저장 경로를 확인할 수 있습니다.
- 해석할 수 없는 파일은 `file_errors/원본` 또는 `file_errors/보안`에 입력 파일 자체를 복사합니다. 읽을 수 없어 복사도 불가능하면 오류를 기록합니다.
- `reports/partition_index.jsonl`(정상 분리 옵션을 끈 경우 `examine_index.jsonl`)은 원본 레코드 주소와 분리 파일을 연결합니다.

전체 결과는 기존처럼 `data`에 보존합니다. 정상 변경/미변경 분리 옵션을 꺼도 위 분류는 저장하며, 검증 미리보기에서는 파일을 생성하지 않고 보고서에 분리 예정 경로를 기록합니다. 이전 버전의 결과 폴더 구조는 자동 변경하지 않습니다.

검토용 `원본`·`보안`은 입력의 필드·배열/객체·중첩 구조와 바깥 메타데이터를 유지합니다. 통합 JSON 전체를 복사하지 않고 해당 레코드만 남깁니다. 여러 건에서 추출할 때는 들여쓰기·숫자 표기 등의 직렬화 형식이 달라질 수 있습니다. JSONL/NDJSON은 해당 줄, CSV는 헤더와 해당 행으로 저장합니다. 처리된 값이 일부 반영되어도 `원본`은 수정 전 입력이며, 처리 후 값은 `data`와 상세 보고서에서 확인합니다.


### 내장 문서의 Mermaid 도식 갱신

아키텍처 문서의 Mermaid 원문은 프로그램 안에서 오프라인 도식으로 표시됩니다. 첫 도식은 문서 최상단에 있고, 부록 두 개도 같은 방식으로 표시합니다. 도식이 있는 문서의 **도식 → 화면에 맞춤 / 100% / 150% / 200%**로 크기를 바꿀 수 있습니다. 도식 이미지는 해당 문서 탭을 처음 열 때 읽습니다.

문서의 Mermaid 코드를 수정한 개발자는 다음 순서로 내장 이미지를 갱신합니다. Node.js 22.13 이상과 Edge 또는 Chrome은 **도식 생성 시에만** 필요합니다. 배포 프로그램에는 설치할 필요가 없습니다.

```powershell
npm ci --prefix tools/mermaid --ignore-scripts
.\.venv\Scripts\python.exe scripts/build_mermaid.py
.\.venv\Scripts\python.exe scripts/build_mermaid.py --check
```

기본 렌더링 브라우저는 Windows Edge입니다. 다른 브라우저는 `--browser "C:/Program Files/Google/Chrome/Application/chrome.exe"`처럼 지정합니다. Mermaid CLI 버전과 개발 의존성은 `tools/mermaid/package-lock.json`으로 고정합니다. `assets/mermaid/`의 PNG·SVG·manifest를 함께 커밋하세요. 패키징 시 현재 MD의 Mermaid 원문 해시와 이미지 해시를 검사합니다.
